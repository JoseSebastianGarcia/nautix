# Release 0.4.0

Branch `release/0.4.0`, built from `main` at `121c574` plus the version bump. No tag exists for it: tags cannot be pushed from the environment that built this release (see "Tagging").

## What is in it

- **Theming**: flat black / white base with an inverted primary button, liquid glass only on floating layers (top bar, inspector, toasts, dialogs), a configurable accent that never uses red, green or yellow and keeps its contrast, and a *Reduce transparency* option (ADR-049).
- **Audit trail with detail**, **volume browser** (download and upload), **built-in help** in English and Spanish with screenshots, **Vaultwarden / Caddy HTTPS / Elasticsearch / Kibana** templates.
- **Canvas and UI polish**: lines leave and arrive by the sides that face each other; connection dots show on hover or selection; the *Connect to Swarm* button is animated; the Gateways page shows each gateway's own wording (it used to show Kong's for all).
- **Specs**: `docs/spec/` brought up to date with what was built (product positioning, web layout and theming, topology and Swarm canvas, commands matrix, roadmap status, testing, guards/bindings/zones addenda).
- **Swarm, in place**: every setting of a service is editable from the canvas (ports, volumes, secrets, configs, environment by name, health check, limits, update policy) as one rolling update; `docs/guides/swarm-two-machines.md` explains how to try Swarm with two machines (ADR-054).
- **Swarm**: its own menu entry and a floating *Connect to Swarm* button; a cluster canvas (overlay networks as boxes, services as nodes, a dot per copy in the colour of its server); services with volumes, placement, secrets and rolling updates that roll back; manual rollback; moving a service between overlays; bindings between services; everything through a plan that waits for the result and undoes itself when a change fails (ADR-045 to ADR-053).

## Where the risk is

1. **Swarm was exercised on two real nodes only on one machine.** Spreading, role constraints, pinning, global services, per-node limits, drain and a dead worker were verified on a real two-node swarm built from two Docker daemons on one host. **The overlay network between two machines was not**: both daemons create the same VXLAN interface, so it needs two real machines (see the guide). The service features themselves (volumes, secrets, configs, health check, limits, rolling update and rollback, bindings) were verified on a single-node swarm.
2. **Removing a service from the canvas cannot be undone** (its settings cannot be read back). Removals run last in a plan.
3. **A volume lives on the node where a copy runs.** A service with volumes starts pinned to a node; unpinning it can start a copy on an empty volume.
4. **Database**: migration v6 (`swarm_bindings`) is new. Nautix takes a copy of the database in `backups/` before migrating; restore it to go back.
5. Elasticsearch and Kibana templates use 9.2.1; the version could not be checked against the registry.

## Tagging

When you can push tags from your machine:

```
git fetch origin
git tag -a v0.4.0 release/0.4.0 -m "Release 0.4.0"
git push origin v0.4.0
```

The release workflow publishes the image to Docker Hub when a tag like this is pushed; do that deliberately.
