# Decisions (ADR log)

Short records of choices that depart from, or fill gaps in, `docs/spec/*`.

## ADR-001 — Web-only, NestJS + React
The earlier native (.NET/WPF) direction is dropped. Nautix is a web app: NestJS API + React SPA served by the API on one port. Supersedes the WPF spike history in git.

## ADR-002 — Versions (verified at M0, Oct 2026)
Node 22 LTS (CI target; Node 24 works too), NestJS 11, Vite 8, React 19, Tailwind 4, TanStack Query 5, Zustand 5, React Flow (`@xyflow/react`) 12, i18next, Vitest 3, TypeScript 5.9, Biome 2. Nest 12 / TS 7 exist but were left out to avoid early-adopter breakage.

## ADR-003 — One `docker` module for the engine resources
Containers, networks, images, volumes and engine info share one port (`DockerEngine`) and one module for now; the spec's per-feature modules split when a feature gets its own port (compose, builds). No abstraction without two real uses.

## ADR-004 — Own thin Docker client over `node:http` + unix socket
No `dockerode`/`undici`: the surface used is small and a mock-daemon test covers it. Engine API pinned to `v1.43`.

## ADR-005 — Dependency injection by explicit `@Inject(Token)`
Ports are abstract classes used as tokens; every constructor parameter uses `@Inject`, so the code runs under `tsx`/esbuild (no `emitDecoratorMetadata`) and under `tsc`.

## ADR-006 — Auth: scrypt, SQLite sessions, no Drizzle yet
`argon2id` needs a native build; Node's built-in `scrypt` (N=16384, r=8, p=1) is used instead. Sessions store only the SHA-256 of the cookie token. `better-sqlite3` is used directly; Drizzle arrives with a schema big enough to need it. CSRF: mutations require `x-nautix-csrf: 1` (not settable cross-site) and a same-host `Origin` when present, on top of `SameSite=Strict`.

## ADR-007 — "Boxes" security model for the topology canvas
- A **network box** is a Docker network; containers inside share it. New boxes default to **isolated** (`--internal`): no route to the internet and none from it.
- **Outside every box** a container is "external": it only sits on the default bridge, and published ports always bind to `127.0.0.1`.
- Binding to `0.0.0.0` needs an explicit per-port checkbox with a warning; the canvas flags such ports in amber.
- Moving a container into a box also disconnects it from the default bridge, otherwise it would keep an outbound route and the box's isolation would be fake.
- The intended public entry is a reverse proxy (Traefik/Nginx/Caddy template) that the user exposes deliberately.

## ADR-008 — Theme tokens
The spec's lime/cyan palette is replaced by a violet accent (matches the approved reference). Dark and light define identical token sets (unit-tested).

## ADR-009 — Server-sent events instead of a WebSocket for engine events
`GET /api/v1/events` (SSE, same session cookie) streams `{kind}` messages from the daemon's `/events` (reconnect backoff 250 ms → 8 s). The client coalesces bursts (150 ms) and invalidates queries; 30 s polling stays as a safety net. SSE is one-way and needs no extra dependency; WebSockets are reserved for the terminal.

## ADR-010 — No shadcn/ui yet
Small hand-written components (`components/ui.tsx`) cover M1. Adopt shadcn when the component count justifies it.

## ADR-011 — Web terminal
`/ws/terminal/:containerId` (library `ws`, MIT). Binary frames carry stdin/stdout, text frames carry JSON control (`resize`). The server requires the session cookie and a same-host `Origin` (browsers always send it; its absence is refused). The adapter creates a Docker exec with `Tty:true` running `bash` or `sh` *inside the container* and hijacks the connection; there is no host shell. Every open/close is written as a JSON audit line. Output arriving before the WebSocket subscribes is buffered, so the first prompt isn't lost.

## ADR-012 — Roles and API tokens
Two roles: `admin` and `viewer`. Viewers are read-only (any non-GET is refused with `errors.readOnly`), cannot open terminals and never receive env values (`includeEnv` on the Compose export). Role is read live from the user row, so demoting/deleting takes effect immediately. API tokens (`nx_…`, 256 bit) are stored as SHA-256, shown once, revocable, and authenticate via `Authorization: Bearer`; bearer requests skip the CSRF header check because they can't be forged cross-site. Nobody can delete themselves or the last admin. The UI hides write controls for viewers as a convenience; the server is the enforcement point.

## ADR-013 — Saved canvas layout
One JSON document in SQLite (`layout` table, row 1), read and written whole: `zones` (absolute position, keyed by network name or `external`) and `nodes` (position relative to the box, keyed by container name). Names are stable across recreation, ids are not. Boxes are draggable and their containers are React Flow children, so they move together; a box grows to keep moved containers inside. Saved positions override the automatic flow only for what the user moved. "Auto layout" clears the saved document after confirmation. Writing the layout is a mutation, so viewers can't. The database helper moved to `shared/sqlite-database.ts` because several modules now open the same file (WAL mode).

## ADR-014 — Compose editor
- **One source of truth: the YAML text.** The visual editor never keeps its own model; every visual edit is a patch applied to the parsed `yaml` Document (`@nautix/compose`), so comments, order, anchors and untouched lines survive byte-for-byte (tested: a no-op edit is identical, a single field change adds exactly one line). A file with syntax errors is never rewritten by the visual editor.
- **Shared pure package** `@nautix/compose` (parse, read model, patches, validation, port parsing) is used by the API (to refuse invalid files and unacknowledged risks) and by the web (live checks), so both always agree.
- **Reuses the canvas.** Services map onto the same container/network shapes as the live topology, so boxes, logos, loopback/public port badges and layout are identical; services naming no network sit in the implicit `default` box, as Compose does. Dragging a service into another box rewrites its `networks`.
- **Undo/redo** is whole-text snapshots (max 200, typing coalesced within 500 ms) shared by visual and YAML edits.
- **YAML view uses CodeMirror 6 (MIT), not Monaco**: far smaller, no web workers or CDN loading, which keeps the strict CSP (`script-src 'self'`). Monaco can replace it if schema autocompletion becomes a priority.
- **Execution** goes through `docker compose -f -` (file on stdin, argument array, no shell, minimal env, 10 min timeout, 512 KB output cap) from the API container, which therefore bundles the docker CLI and compose plugin. One operation per project at a time. `up` is refused when the file has errors, and when it uses privileged mode, host network/PID, the Docker socket or powerful capabilities unless the request acknowledges the risks (the UI asks). `down` works even for an invalid file. Relative bind mounts cannot work (the daemon resolves paths on the host), the editor warns about them; use absolute paths or named volumes.
- Projects are stored in SQLite. Importing a directory of existing compose files (the spec's "projects root") is not implemented yet.

## ADR-015 — The Nautix container is locked (replaces the typed confirmation)
The container running Nautix (matched by hostname = container id, or `NAUTIX_SELF_NAME`) cannot be stopped, killed, restarted, paused, removed, attached to or detached from networks, or opened in a terminal through Nautix, for any role or API token (`403 errors.selfLocked`). Starting it is still allowed (harmless). There is deliberately no override flag: if it must change, use the Docker CLI on the host. The UI shows a lock note and does not offer those actions. The earlier "type the name to confirm" flow was removed.

## ADR-016 — Saved templates and storage
Built-in templates live in code (`@nautix/contracts`); templates users save from the deploy dialog (image, ports, env values, data paths, command) are JSON rows in the SQLite database and are merged into `GET /api/v1/catalog`. All server-side configuration is in the data directory (`/data` in the container, the `nautix-data` volume): `nautix.db` holds users, hashed sessions and tokens, the canvas layout, saved templates and Compose projects.

## ADR-017 — Tunnels between network boxes
Docker networks can't talk to each other, and bridging them by attaching a service to both exposes everything it listens on. A **tunnel** is instead a `alpine/socat` container (pinned tag) attached to the source network at creation and to the destination right after; it listens on one port in the source network and relays that TCP port to `target:port` in the destination. Only that port crosses; nothing is published on the host; the target must be a (non-tunnel) container on the destination network. It is labelled `nautix.tunnel*` so the UI draws it as a line between boxes (dragging from one box's connector dot to another's) instead of as a node, and it is removed like any container. Every container on the source network can reach the tunnel port, not just one — the dialog says so. TCP only for now (UDP would need a second socat).

## ADR-018 — API gateway routes (Kong, DB-less)
Mappings (path and/or domain → upstream URL, strip-path flag) are edited in the **Gateway** page, stored in SQLite per gateway container name, and pushed as a Kong declarative config to `POST :8001/config`. Nautix's own container is locked and not on the gateway's network, and Kong's image can't be assumed to ship curl, so a short-lived helper (`curlimages/curl`, pinned) joins the gateway's user network, posts the YAML (passed in an environment variable and only expanded as a quoted shell value, so route data never becomes shell syntax) and is removed again. Upstreams are chosen from containers sharing a network with the gateway, tunnels included, or typed as any http(s) URL without credentials. DB-less Kong keeps its config in memory, so after a restart the saved routes are re-sent with "Apply again". Only Kong is detected (by image); other gateways would add a builder next to `kong-config.ts`.

## ADR-019 — One gateway strategy per kind (Kong, Nginx, Caddy, Traefik)
The Gateway page works with any supported gateway or reverse proxy. The kind is detected from the image (`gatewayKind`) and a `GatewayStrategy` (abstract base: `plan(routes)` rejects duplicate routes, then `build`) produces the plan: Kong posts declarative YAML through the helper container (ADR-018); Nginx and Caddy get a generated config written next to the live one, validated and reloaded inside the container; Traefik gets a file-provider YAML in `/etc/traefik/dynamic` (watched, no reload). Proxies other than Kong take upstreams without a URL path. Adding a kind = one strategy class plus an entry in `GATEWAY_INFO`. HAProxy (added later) gets a `haproxy.cfg` swapped in after `haproxy -c` and a master-process reload (`kill -USR2 1`); its template starts with a tiny stub config because the image ships none and runs unprivileged, and gateway commands run as root so they can swap files the archive API wrote. APISIX and WSO2 are not supported yet. The Traefik template now uses the file provider, so existing Traefik containers must be redeployed.

## ADR-020 — Simplified navigation
Five top-level entries: Topology, Resources (containers, images, volumes, networks as a secondary tab bar), Compose, Gateways, System. Settings is a gear next to logout (admin only).

## ADR-021 — Native HTTPS
`NAUTIX_TLS=auto` makes the API serve HTTPS itself with an ECDSA self-signed certificate (`selfsigned`, MIT) stored in `<data>/tls`, valid for localhost, 127.0.0.1, ::1 and `NAUTIX_TLS_HOSTS`; it is reissued when it expires within 30 days or a requested host is missing. `NAUTIX_TLS_CERT` + `NAUTIX_TLS_KEY` use the operator's own PEM files instead. Either way session cookies become `Secure` (the same-host Origin checks and `wss://` for the terminal already follow the page scheme). No HSTS is sent, so a browser warning on a self-signed certificate can still be bypassed. Default for `pnpm start` stays plain HTTP on 127.0.0.1; the compose file enables `auto`.

## ADR-022 — Certificates managed from Nautix (local CA)
A public CA (Let's Encrypt) cannot issue for `localhost` or private names, so a "valid" certificate for local use means one signed by a CA the operator trusts. Nautix keeps a local root CA (EC P-256, 10 years, `<data>/tls/ca.pem` + 0600 key) and issues the server certificate from it (825 days, SANs: localhost, 127.0.0.1, ::1 and the names/IPs saved in the UI). The CA's public part is downloadable from Settings and must be installed once per machine. Hosts changes and custom certificates are applied to the live listener with `setSecureContext`, no restart. Custom PEM pairs are validated (key matches, not expired). ACME for public domains is not implemented. Replaces the env-only self-signed flow of ADR-021.

## ADR-023 — Secrets at rest and password hashing
Registry logins (login/logout) are stored in SQLite with the password sealed by AES-256-GCM (`v1.<iv>.<tag>.<ciphertext>`); the 32-byte key is generated on first use in `<data>/.key` (0600). A login is saved only after the registry accepts it; pull and push look it up by the image's registry (Docker Hub aliases folded into `docker.io`), typed credentials win, and passwords are never returned by the API. Backups must keep `.key` together with `nautix.db`. User passwords stay on Node's built-in scrypt (N=16384, r=8, p=1, unique salt, constant-time compare) instead of argon2id: same class of memory-hard KDF without a native dependency in the image; swap behind the `PasswordHasher` port if policy demands argon2.

## ADR-024 — Builds and the Dockerfile editor
`@nautix/dockerfile` (pure TS, shared by web and tests) parses Dockerfiles (continuations, comments, heredocs, stages) and lints them with rules `NX-DF001…013` that each have a positive and a negative test; some carry a quick fix. The Builds page (Resources → Builds) streams `POST /api/v1/builds` as plain text ending in `NAUTIX-BUILD: ok|failed`, because the HTTP status is already sent when a build step fails. The API builds a tar context from the typed Dockerfile plus small text files and calls the engine's `/build` (classic builder: build args, target, no-cache, pull). BuildKit features (DAG with timings, secrets, buildx, bake, builders) are not covered; they would need the `docker buildx` CLI in the image. The editor text is kept in `localStorage`.

## ADR-025 — Swarm
Swarm lives in its own module behind a `SwarmEngine` port (socket adapter, in-memory fake for the demo and tests) with one CQRS handler per use case. Services, nodes, secrets and configs use the Engine API; `docker stack deploy|rm` is the only CLI part (argument array, file on stdin, minimal environment) because stacks are a client-side feature. Stacks are listed from the `com.docker.stack.namespace` service label. Join tokens, the unlock key and config contents are admin-only reads; secret values are write-only and never returned. A swarm service port is published on every node on all interfaces, so the new-service dialog warns about it. Integration tests run a real swarm (create, scale, logs, secrets, configs, stack deploy/rm).

## ADR-026 — License: Apache-2.0
The project moved from MIT to Apache-2.0 (explicit patent grant, `NOTICE` file). All code so far was written for Patterna, so relicensing needs no third-party consent; contributions from now on are accepted under Apache-2.0. Dependencies must stay compatible (MIT, Apache-2.0, BSD, ISC, MPL ok; GPL, AGPL, SSPL, BUSL no), enforced by `scripts/check-licenses.mjs`.

## ADR-027 — License: SSPL-1.0
The project moved from Apache-2.0 to the Server Side Public License v1 to discourage third parties from offering Nautix as a hosted service without opening their service stack. The text in `LICENSE` is the unmodified SSPL v1 (MongoDB's copy); the copyright notice is in `NOTICE`. SSPL is source-available and not OSI-approved: some distributions and companies do not allow it. The repository was private when this changed, so no one received earlier versions under MIT or Apache-2.0. Dependencies still must not be GPL, AGPL, SSPL or BUSL (`scripts/check-licenses.mjs`): permissive dependencies (MIT, Apache-2.0, BSD, ISC, MPL) can be combined with SSPL code.
The `LICENSE` file starts with a Nautix header (owner, what the Program is, version 1 only, no "or any later version") followed by the unmodified SSPL text: the license forbids changing its words, so mentions of its author (MongoDB, Inc.) stay, since they refer to who wrote the license, not to the project's owner. Writing different terms would make it a custom license and needs a lawyer.

## ADR-029 — Password changes and emergency recovery
Changing your own password needs the current one (rate-limited) and signs every other session out; viewers may do it too (`@SelfService()` lets a mutation through the read-only role check). An admin can set another user's password, which signs that user out everywhere. Recovery of a lost admin is a CLI that runs next to the database (`node dist/cli.js reset-password|create-admin <user>`): anyone who can run commands in the container already controls the host. It prints a random 24-character password once and writes an `cli` audit entry. There is deliberately no email-based reset (no mail server in a self-hosted tool) and no "forgot password" link.

## ADR-030 — Versioned SQLite migrations (SQLite stays)
The schema now lives in one ordered list (`shared/db/schema.ts`) applied by a small runner (`shared/db/migrations.ts`) that records each version in `schema_migrations`. Every migration runs in its own transaction; a failure leaves the database at the last version that applied. Version 1 is the baseline of everything that existed before (all `IF NOT EXISTS`, so installs from earlier versions adopt it without changes). Before upgrading a database that holds data, Nautix takes a consistent copy with `VACUUM INTO` in `<data>/backups/pre-migrate-from-vN-<time>.db` (the last five are kept). A database from a newer Nautix is refused with a clear error instead of being opened, and restoring such a backup is rejected up front. To change the schema: append a migration with the next number, never edit a shipped one. Repositories no longer create tables themselves. SQLite remains the store (one instance, a single file to back up); the `*Repository` ports keep PostgreSQL possible later.

## ADR-031 — Updates are manual
There is no "update Nautix" button. The container is locked against changes from its own UI, a self-update needs a second helper container with the Docker socket, and a failed update would take the UI down exactly when it is needed. Updating is two commands (see the README); the database is copied to `/data/backups` before any schema upgrade, and a database from a newer version is refused, so a rollback is: run the previous image tag with the previous backup. Pin a version tag (`NAUTIX_VERSION=0.1.0`) if you want updates only when you choose.

## ADR-032 — Custom DNS records (dnsmasq)
The DNS tab edits records for `dockurr/dnsmasq` containers only: the image reads every `/etc/dnsmasq.d/*.conf`, so Nautix owns exactly one file there (`nautix.conf`) and never touches the rest. The template was switched from `jpillora/dnsmasq` (config file only, no drop-in directory, web editor that fought with ours) and keeps `/etc/dnsmasq.d` in a volume. Records are stored in SQLite per container name (migration v2) and are the source of truth: apply writes `nautix.conf.new`, validates it with `dnsmasq --test`, swaps it in and restarts the container, since dnsmasq reads its configuration only at start. Each record is `address=/name/ip`, which also answers for subdomains; a name may have one IPv4 and one IPv6 address. Names and IPs are validated in the contract and again before they reach the file, so a value can never add another directive. AdGuard Home (REST rewrites behind its own login) and Pi-hole (config format differs between v5 and v6) are listed but not editable yet. Tested against a real dnsmasq: answers, subdomains, IPv6, lookup from another container, and persistence across a restart.

## ADR-033 — Menu: four entries
Gateways and DNS moved into the Resources tabs (Containers, Images, Volumes, Networks, Builds, Gateways, DNS, Swarm) because they are things you configure on resources, so the top bar is now Topology, Resources, Compose and System (Settings stays the gear). Supersedes the five-entry layout of ADR-020.

## ADR-034 — Fixed IPs are optional
By default Docker assigns the address. A container can be given a fixed IPv4 on a network you created, at deploy time (`ipAddress`) or later (`PUT /containers/:id/fixed-ip`, `ip: null` hands it back to Docker). The address must lie in the network's subnet, not be its network, broadcast or first (gateway) address, and not be used by another container there; the same check runs in the browser and the API (`checkFixedIp`). Docker only takes the address when a container joins a network, so changing it on a running container reconnects it to that network (a short drop of connections through it; if the new address is refused the container is put back automatically). The default bridge and IPv6 are not covered. Verified against a real daemon: the address survives restarts, a duplicate is refused, and pin/release work on an existing container.

## ADR-035 — Visual Dockerfile editor: text stays the source of truth
Like the Compose editor, the blocks view never keeps its own model: it parses the text, and every change is a patch of the lines of one instruction (`replaceInstruction`, `removeInstruction`, `moveInstruction`, `insertInstruction` in `@nautix/dockerfile`). Comments directly above an instruction travel with it when it is moved or deleted; parser directives (`# syntax=`, `# escape=`) and blank lines are never touched; CRLF files stay CRLF. Each instruction type has a form model (`parseForm` / `formToArgs`) that does not unquote anything, so editing one field cannot rewrite another; shapes it cannot model (unknown flags, odd `HEALTHCHECK`) fall back to a raw text field instead of being lossy. An edited multi-line `RUN` is rewritten with `\` continuations (its original line breaks are not preserved). Form fields keep their own draft because the model is re-parsed and trimmed after each keystroke. Undo/redo are whole-text snapshots shared by the blocks and code views. Reordering by mouse has a keyboard equivalent (move up/down). Not built: per-instruction build timings (needs BuildKit), a byte-exact corpus of 150 real Dockerfiles, and project detection from a folder (the templates cover the common starts).

## ADR-036 — DNS adapters (strategy per server), like the gateways
Records are stored per container in SQLite; a `DnsStrategy` per server type (`dns-strategies/`, registry in `index.ts`, detection by image in `@nautix/contracts`) turns them into a plan: files to write, commands to check them, and how the server picks them up (`restart`, or `reload` watched through the server's logs). One handler applies any of them. dnsmasq (`dockurr/dnsmasq`): `/etc/dnsmasq.d/nautix.conf` validated with `dnsmasq --test`, then restart. CoreDNS: its Corefile, written whole, with one `template` block per record and family (name and subdomains, most specific first, empty NOERROR for the family a name does not have) and `forward . /etc/resolv.conf`; no shell exists in that image, so there is no pre-check, the `reload` plugin applies it without dropping queries and Nautix reports the reload outcome from the logs; it also cannot boot without a Corefile, so the first apply writes into the stopped container and starts it. "Test" no longer runs `nslookup` inside the DNS container (impossible for CoreDNS): a throw-away container joins the server's network and queries it, which also proves the network path. Pi-hole and AdGuard Home are recognised but not editable: both are managed through an authenticated API/UI and need credentials stored per server; unbound and BIND need image-specific paths. Each new adapter is one class plus a line in the registry.

## ADR-037 — Dockerfile wizard, pieces and folder build context
"Recipes" (`@nautix/dockerfile/recipes`) are pure functions from a few answers to a Dockerfile plus its helper files (`.dockerignore`, `nginx.conf`), so the browser preview and the tests run the same code and every recipe must pass the linter without warnings. The .NET recipes follow the official image layout (`sdk:10.0` to `aspnet:10.0[-alpine|-noble-chiseled]`, `USER $APP_UID`, `ASPNETCORE_HTTP_PORTS`, invariant globalization on Alpine) and copy the project files before `dotnet restore` so the restore layer is cached; the Debian and chiseled runtimes have no wget/curl, so they get no `HEALTHCHECK` and the wizard says so. "Pieces" are multi-instruction snippets inserted before a chosen line from the "+" between cards; two lint rules protect the order they encourage (NX-DF014 copy-all before restore, NX-DF015 build steps after CMD/ENTRYPOINT). A build can now use a project folder: the browser filters it with `.dockerignore`, writes a tar (no copy in memory: `File` objects are tar parts) and streams it to `POST /api/v1/builds/context?options=…` (512 MB cap, options validated like the JSON build); the editor's Dockerfile replaces any `Dockerfile` in the folder. Not built: Git URL contexts (`remote=`), BuildKit-only features such as secrets mounts.

## ADR-038 — DNS records can point at a container by name
A saved record is `{name, ip}` or `{name, container}` (`DnsEntry`); the adapters still receive only resolved `{name, ip}`. Container targets are resolved when the records are applied (IPv4 on a network shared with the DNS server first, else the first one), so the name follows the container when it is recreated with another address; apply fails with `dnsTargetMissing` / `dnsTargetNoIp` if the container is gone or stopped. A container target counts as the IPv4 record of its name. Records saved before this change keep working (same JSON shape). Not built: re-applying automatically when a container's IP changes; the user presses "Save and apply".

## ADR-039 — Port exposure (guards, level 1)
The exposure of a port is derived from the host IP of its real binding (`exposureOf`), so containers created outside Nautix are classified too: `127.0.0.1`/`::1` local, `0.0.0.0`/`::`/empty open, anything else a specific address. Changing it recreates the container (`DockerEngine.rebindPorts`, plan built by the pure `planRebind`): same config, host ports (including engine-assigned ones), fixed IP and aliases on the primary network, the other networks reconnected, anonymous volumes pinned by name so no data is lost (Docker omits `Name` for some of them, the name is read from the mount path), generated hostname dropped. The old container is parked under a temporary name, stopped, and removed only after the new one is up; on any failure the new one is deleted and the old one renamed back and restarted. Nautix itself cannot be rebound from the UI. Host interfaces are not listed because Nautix runs in a container and would only see its own: the address is typed and validated. Verified on a real daemon, including the volume case that the first version got wrong.

## ADR-040 — Allow lists on gateway routes (guards, level 2)
`GatewayRoute.allow` is a list of CIDRs or single addresses (empty = no filter; routes saved before the field existed load with an empty list). Each adapter renders its native mechanism: nginx `allow`/`deny all` in the location, Caddy `@blocked not remote_ip` + `respond 403`, Traefik an `ipAllowList` middleware ahead of the prefix strip, HAProxy an `src` ACL with `http-request deny deny_status 403` for that route's conditions, Kong the `ip-restriction` plugin. `isCidr` and `cidrContains` are pure (no `node:net`) and shared by the API and the editor, which suggests the caller's address (`GET /gateways/client-address`) and warns when the list excludes it. The address a gateway sees is what reaches it: behind another proxy, or with local traffic going through Docker's userland proxy, that can be the proxy or the Docker gateway rather than the real client; the editor says so and Nautix does not try to read `X-Forwarded-For`. Verified on real Nginx, Caddy and HAProxy (listed network answers, another gets 403); Traefik and Kong are covered by rendering tests only.
